# AgriEdge Render + Neon deployment preparation

## Prepared configuration

[`../render.yaml`](../render.yaml) defines the existing Vite app as a Render Static Site and FastAPI as a Render Python web service. It keeps automatic deployment off, builds the existing React app, uses the `/prices` SPA rewrite, runs `alembic upgrade head` as the API pre-deploy step, and uses `/health` for its health check. Render's assigned API URL is passed to the static build as `VITE_API_BASE_URL`; the assigned frontend URL is passed to FastAPI as its exact `CORS_ORIGINS` origin. API signing and phone-hash secrets are generated by Render and are not stored in this repository. The Neon `DATABASE_URL` is deliberately a dashboard-only secret (`sync: false`). Judge mode is read-only: anonymous GET/HEAD requests resolve only to the explicitly seeded demo farmer, writes require a bearer token, and registration is disabled. No login or registration UI is included. Static headers mark `sw.js` as revalidatable, the manifest with its web manifest MIME type, and model/WASM files with binary/WASM MIME types.

The frontend's existing service worker, TFLite model, metadata, and WASM runtime are under `frontend/public/`; Vite copies these files into `frontend/dist/` unchanged. Render's static site serves them at their existing root paths, and the existing worker caches them. The `/*` rewrite provides deep-link fallback for React Router while existing static files continue to be served.

## Backend configuration safeguards

- `DATABASE_URL` is environment-based. PostgreSQL URLs are normalized to SQLAlchemy's `postgresql+asyncpg` driver. Neon `sslmode` is converted to asyncpg's `ssl`; its unsupported `channel_binding` query option is removed. TLS remains required when Neon supplies `sslmode=require`.
- `asyncpg` is pinned in `backend/requirements.txt`; `.python-version` pins the Render API runtime to the locally verified Python version.
- Production startup rejects debug mode, a missing/short/demo `SECRET_KEY`, non-PostgreSQL database URLs, and CORS values that are not HTTPS origins. Errors name the invalid variable without printing its configured value.
- The API no longer calls SQLAlchemy `create_all` in production. Render's pre-deploy Alembic command owns schema changes; local development and tests retain their current creation behavior.

## Existing SQLite data and safe migration

The current `backend/agriedge.db` was inspected through a read-only connection. It is at Alembic revision `418405211d15` and contains 60 rows: 30 scan logs, 8 irrigation decision logs, 7 sensor readings, 4 farm sectors, 4 reference price rows, 2 farmers, 2 listings, and one each of farms, disease reports, and irrigation schedules. Offers and outbreak tables currently have zero rows. No row contents were displayed or changed.

Production should start with a fresh, empty persistent Neon database. Do not import these 60 SQLite rows as part of this deployment. The local database remains the preserved development copy/backup. [`../backend/scripts/migrate_sqlite_to_postgres.py`](../backend/scripts/migrate_sqlite_to_postgres.py) is an optional append-only importer for a separately approved future data-transfer project; it opens SQLite read-only and refuses a non-empty target. It has not been run.

Validate the schema on a disposable Neon branch first. From `backend`, set `DATABASE_URL` in the current shell to that branch's **direct** connection URL and run:

```powershell
& ".venv\Scripts\python.exe" -m alembic upgrade head
```

Inspect the new schema and run isolated application smoke tests. After validation, create a separate fresh persistent production Neon database and apply the same Alembic migrations; do not point Render at the disposable branch. Keep `backend/agriedge.db` untouched as the local backup. The importer is not part of this production setup sequence.

## Required Render environment variables

| Service | Variable | Value/source |
| --- | --- | --- |
| API | `ENV` | `production` (Blueprint) |
| API | `DEBUG` | `false` (Blueprint) |
| API | `SECRET_KEY` | Render-generated 256-bit value (Blueprint) |
| API | `PHONE_HASH_SECRET` | Render-generated stable key for farmer login identifiers (Blueprint; retain across redeployments) |
| API | `DEMO_READ_ONLY` | `true` for judge mode; anonymous access is limited to seeded demo farmer GET/HEAD routes |
| API | `ALLOW_REGISTRATION` | `false` while judge demo mode is enabled |
| API | `DATABASE_URL` | Neon direct PostgreSQL connection string entered in Render secret settings; no value belongs in Git |
| API | `CORS_ORIGINS` | Render frontend `RENDER_EXTERNAL_URL` reference; update if serving from a custom frontend domain |
| Frontend build | `VITE_API_BASE_URL` | Render API `RENDER_EXTERNAL_URL` reference; rebuild after changing the API/custom domain |

For Neon, choose the same region as the Render API where possible and use the direct (non-pooler) URL for migrations. The URL's TLS query option is normalized for asyncpg. Do not paste the URL into logs, issues, or source files.

## Review blockers before public exposure

1. Judge mode requires the demo seeder to be run once against the fresh Neon database after migrations. It creates clearly identified demo data only; do not run the SQLite importer or point the seeder at the local development database.
2. Browser demo access is intentionally read-only. Anonymous GET/HEAD access is limited to the seeded demo farmer's records; registration and anonymous writes are disabled. Marketplace mutations require an authenticated account, and the retained UI intentionally has no login page. Private farmer records remain owner-scoped.
3. Neon has not been provisioned and the SQLite importer has not been run against PostgreSQL. Rehearse Alembic migrations against a disposable Neon branch first, then create a fresh persistent production database. Do not import local SQLite rows.
4. After the repository push, provision Neon and set `DATABASE_URL` only in Render's secret settings, then sync the Blueprint. Test health, frontend/API connectivity, anonymous read-only demo access, rejected writes, model downloads, direct SPA routes, service-worker cache, and offline diagnosis before public release.
